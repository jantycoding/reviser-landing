# Reviser — оплата, код доступа и операционка конвейера

> Снимок документа из проекта claude.ai на 05.08.2026.
> **Статус на 07.08.2026:** бэкенд не построен, `VITE_PAY_ENDPOINT` не задан,
> счёт выставляется вручную в WhatsApp. Это осознанное решение на время

> ручная выдача счетов начнёт съедать больше часа в день.

## 1. Оплата → код → агент

### Схема

```
Сайт  ──POST /invoice──►  ваш бэкенд  ──►  ApiPay/PayBot  ──►  Kaspi
                              │
                              │◄──webhook «оплачено»── ApiPay/PayBot
                              ▼
                         БД: заказ = paid, код активен
                              │
Клиент жмёт «Открыть WhatsApp с кодом» ──► агент ──GET /verify?code=──► бэкенд
                                              «оплатил, начинай анкету»
```

### Эндпоинты бэкенда

| Метод | Путь | Что делает |
|---|---|---|
| POST | `/invoice` | Принимает `{name, phone, product, amount}`. Создаёт счёт у провайдера, генерирует код, пишет заказ в БД. Возвращает `{code, payUrl, qr}` |
| POST | `/webhook` | Уведомление об оплате от провайдера. **Обязательно проверяет подпись.** Ставит `status=paid` |
| GET | `/status?code=` | Для сайта: опрос состояния, чтобы показать «Оплачено» без перезагрузки |
| GET | `/verify?code=` | Для WhatsApp-агента. Только по секретному заголовку. Возвращает `{valid, status, name, phone}` и помечает код использованным |

Фронтенд уже написан под этот контракт: задаётся `VITE_PAY_ENDPOINT`,
и блок оплаты сам переключается из запасного режима в боевой.

### Формат кода

`RV-XXXXXX`, где X — из алфавита `23456789ABCDEFGHJKLMNPQRSTUVWXYZ` (без похожих
0/O и 1/I, чтобы не путали при переписывании). Это ~1 млрд комбинаций.

### Таблица заказов

```
id · code · name · phone · amount · product
provider_invoice_id · status (created|paid|used|refunded)
created_at · paid_at · used_at · used_by_phone
```

### Что обязательно учесть

**Проверка подписи вебхука.** Без неё любой, кто узнает URL, помечает свои
заказы оплаченными. Это не теоретический риск, а первое, что пробуют.

**Телефон собираем до оплаты.** Он уже есть в форме. Это даёт запасной канал:
если клиент оплатил и пропал, вы знаете, кому написать.

**Кто пишет первым — важно.** WhatsApp Business API требует одобренный шаблон,
чтобы бизнес инициировал диалог вне 24-часового окна. Поэтому основной путь на
сайте — кнопка «Открыть WhatsApp с кодом»: клиент пишет сам, окно открывается,
шаблон не нужен.

**Код одноразовый, но с человеческим допуском.** Помечаем использованным и
привязываем к номеру. Если клиент потерял переписку и пишет с того же номера —
пускаем. С чужого — нет.

**Rate limit на `/verify`.** Иначе код можно подобрать перебором.

**Дублируйте код.** Показываем на экране, отправляем в SMS и на почту. Люди
закрывают вкладку.

### Провайдер

Стартуем на посреднике (ApiPay.kz или PayBot.kz) — подключение за 15 минут,
подписка вместо процента. Параллельно подаём заявку на официальный
интернет-эквайринг Kaspi (`kaspi.kz/webpay/partnership`, рассмотрение 6–15
рабочих дней) и переезжаем, когда одобрят. Заявка лежит две недели сама по себе,
так что подать её стоит в первый же день.

## 2. Операционка конвейера

Папка в облаке — это хранилище файлов, а конвейеру нужна ещё и система
состояний. Три слоя.

### Слой 1. Таблица — источник правды

Airtable или Notion на старте. Одна строка = один клиент:

```
код заказа · имя · телефон · ниша · дата оплаты
статус: оплачен → анкета → доступы → разбор → отчёт → созвон → закрыт
доступы: CRM ✓ / реклама ✓ / карты — / соцсети ✓  (по каждой платформе)
находок: 14 · из них под агентов: 6
продано после: план роста ✓ / внедрение —
ответственный
```

Именно эта таблица отвечает на вопрос «у кого что застряло» — папки на него не
отвечают никогда.

### Слой 2. Папка по шаблону

Создаётся автоматически при оплате, всегда одинаковая:

```
/Клиенты/2026-08-05-название/
  00-входные/       анкета, NDA
  01-выгрузки/      CRM, звонки, переписки, скриншоты
  02-находки/       JSON от агентов, по файлу на направление
  03-отчёт/         PDF + исходник
  04-созвон/        запись, заметки, что продали
```

Одинаковая структура — обязательное условие: только так поверх неё можно
запустить автоматику.

### Слой 3. Отчёт из структурных данных

Ключевой момент, который превращает ручную работу в конвейер: **агенты пишут не
текст, а JSON**.

```json
{
  "area": "Обработка заявок",
  "finding": "4 из 10 лидов без повторного касания",
  "evidence": ["сделка #4821, 14.07", "сделка #4877, 19.07"],
  "impact": "high",
  "solution": "agent",
  "agent_spec": "Догрев: 3 касания в течение 48 часов"
}
```

Из массива таких объектов PDF рендерится по шаблону. Что это даёт:

- отчёт всегда одинакового качества и вёрстки, без ручной сборки;
- поле `solution` автоматически делит находки на «агент» и «своими силами» — это
  же деление показано на сайте;
- поле `agent_spec` — готовое ТЗ на внедрение, то есть коммерческое предложение
  собирается из отчёта само;
- расход токенов режется в разы: модель заполняет схему, а не пишет сочинение.

### Доступы — отдельно

Пароли и гостевые доступы не хранятся в той же папке, что отчёты. Менеджер
паролей (1Password, Bitwarden) с ролевым доступом. Причина простая: папку с
отчётом рано или поздно кто-нибудь расшарит.

Позиция по паролям: просим не пароли, а гостевой доступ на чтение. Meta, amoCRM
и Bitrix прямо запрещают передачу учётных данных, вход в чужой кабинет по
паролю — типовой триггер блокировки обоих аккаунтов. На сайте это уже написано,
и это же ваше конкурентное преимущество перед теми, кто просит пароли.

## 3. Как экономить токены в разборе

Себестоимость разбора и есть маржа при конвейере.

**Собирать данные детерминированно.** Выгрузки, счётчики, рейтинги, объёмы —
скриптами и через API. Модель включается только там, где нужно суждение.

**Разделять модели по задачам.** Классификация и разметка — на дешёвой модели.
Синтез выводов и приоритизацию — на сильной. Не гонять всё через одну.

**Заполнение схемы вместо свободного текста.** Структурный вывод и короче, и
стабильнее, и его не надо переписывать.

**Кэширование префикса промпта.** Методика направления одинакова для всех
клиентов — она должна кэшироваться, а не пересылаться каждый раз.

**Батчинг.** Звонки и переписки обрабатываются пачками, а не по одному.

**Порядок работы:** сбор → нормализация → 12 направлений параллельно →
дедупликация находок → приоритизация → сверка аналитиком → рендер PDF.
Сверка человеком остаётся: она стоит 20 минут и защищает от выдуманных фактов,
за отсутствие которых вы отвечаете на сайте.

## 4. Что сделать по порядку

1. Зарегистрироваться в ApiPay.kz или PayBot.kz, подключить кассу Kaspi Pay.
2. Параллельно подать заявку на официальный эквайринг Kaspi.
3. Поднять бэкенд с четырьмя эндпоинтами выше (небольшой сервис, день работы).
4. Прописать `VITE_PAY_ENDPOINT` — блок оплаты на сайте переключится сам.
5. Завести таблицу-источник правды и шаблон папки.
6. Написать инструкцию по выдаче гостевых доступов со скриншотами — она нужна
   агенту на третьем шаге воронки.
7. Собрать первый разбор руками, на нём зафиксировать схему JSON, и только потом
   автоматизировать.
